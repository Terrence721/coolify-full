# Smoke Test

<!-- markdownlint-disable-next-line MD036 -->
**Last Updated: July 28, 2026**

A manual, browser-based checklist for verifying the app actually works end-to-end — the thing every phase of [`docs/livewire-to-react-migration.md`](livewire-to-react-migration.md) explicitly skipped in favor of automated checks (Pint/Pest/`yarn build`). The Livewire→React migration itself completed 2026-07-14; this checklist now serves as a standing regression suite — run it after any batch of work touching these flows, not just migration work. See [`docs/command.md`](command.md) for the commands to start the dev stack.

This checklist is the third of three testing layers — Pest (backend), Vitest (frontend in isolation), and this file (real browser, real HTTP) — each blind to what the other two cover. See the **[rendered diagram](https://terrence721.github.io/coolify-full/diagrams/testing-strategy-layers.html)** for what each layer actually proves, with real examples of bugs only one layer caught.

Check items off as `[x]` as you go, or just read top to bottom and confirm each still works. If something fails, note the page and the exact error (console + Laravel Debugbar) before fixing — that detail is what makes a bug report actionable.

**Keep "Preserve log" off by default, so stale Console entries don't get mistaken for live errors.** Correction, 2026-07-20: an earlier version of this note wrongly wrote off a persistent red badge/"N hidden" counter in DevTools' Console toolbar as an unrelated DevTools-level notification. It wasn't — it was real, but *stale*: with "Preserve log" checked, old error entries survive page navigations and even logout/login, so errors from an earlier, already-fixed problem (in this case, the ad-blocker-blocks-WebSockets issue documented in `DEVELOPING_IN_CONTAINERS_WINDOWS.md`) kept counting toward the badge long after the real issue was resolved, making a clean session look like it still had a live error. Confirmed via Laravel Boost's `browser-logs` (captures real console errors server-side in real time, independent of DevTools' own UI/filtering) — no new errors had actually been logged from the real browser in hours, only from old, preserved entries. **Practice going forward**: leave **"Preserve log" OFF by default.** Unchecked, Chromium-based DevTools (Edge included) auto-clears the Console on every navigation/reload — free, built-in protection against exactly this stale-entry problem, no manual clicking or scripting needed. Only flip it **on** temporarily for the specific checks that need history to survive a navigation (e.g. item 6 below, confirming no full-page reload happened — a real reload would otherwise silently clear the log for you, which is itself part of the signal), then flip it back off afterward. If you need a one-off manual reset mid-check, typing `console.clear()` into the Console's command-line prompt is faster than hunting for the icon.

**Clean up throwaway resources through the real delete flow (UI click-through or the REST API), never a raw `tinker` `->delete()`/`->forceDelete()` on the model.** Found 2026-07-25: two throwaway applications created during earlier smoke-test passes (2026-07-23, 2026-07-24) were "cleaned up" by deleting their `Application` row directly in `tinker`. `Application::booted()` has no `deleting()`/`deleted()` hook, so that removed the database row without ever touching the real Docker container — both sat running for 20-42 hours afterward with zero corresponding DB record, only discoverable by cross-referencing `docker ps -a`'s `coolify.managed=true`-labeled containers against the database directly. Real teardown (stopping/removing the container, its Compose project, its Traefik/Caddy labels) only happens through the actual delete Action, reached via the UI's own Delete button or a REST call like `DELETE /api/v1/services/{uuid}` — confirmed by using exactly that path for the 2026-07-25 service-database backups smoke test's own throwaway Gitea+Postgres service, and verifying via `docker ps -a` that the containers actually disappeared before moving on, not just the DB row. If a throwaway resource genuinely needs DB-only manipulation (e.g. a direct-insert fixture that was never deployed and has no container at all), that's fine — the rule is specifically about anything that got a real container running.
